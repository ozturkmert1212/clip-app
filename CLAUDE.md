# ClipApp

An "instant replay" clipping app for macOS. Once the user starts clipping it captures the screen continuously, keeps the last N seconds in memory already encoded, and saves them as an mp4 on a global shortcut. The main window lists the saved clips, plays and trims them; the menu bar icon stays as a helper.

## Build / run

```bash
xcodegen generate            # project.yml -> ClipApp.xcodeproj (not kept in the repo)
xcodebuild -project ClipApp.xcodeproj -scheme ClipApp -configuration Debug -derivedDataPath build build
open build/Build/Products/Debug/ClipApp.app
```

For a release build use `-configuration Release`; the output is `build/Build/Products/Release/ClipApp.app`. The app target is arm64 only (`ARCHS: arm64`). `scripts/release.sh` packages a Developer ID signed, notarized and stapled dmg into `dist/` (notary profile `ClipApp` in the keychain); see "Releasing" below for the whole order. Pass the Developer ID certificate as its SHA-1 hash, `IDENTITY="F530879D8F391FDD191902415739BEF130C263D4" scripts/release.sh`, because the certificate name contains a non-ASCII character. The app is notarized (as a zip) and stapled first, then put into the dmg, which is notarized and stapled in turn: two submissions, and the app passes Gatekeeper offline once copied out. Without a Developer ID certificate run it as `IDENTITY="Apple Development" scripts/release.sh --no-notarize`.

- After adding or removing files, run `xcodegen generate` again.
- `ClipApp/Info.plist` and `ClipApp/ClipApp.entitlements` are generated by XcodeGen from `project.yml`; change them through `project.yml`, not by hand.
- Signing is automatic with an Apple Development certificate (`DEVELOPMENT_TEAM: CRHSYX58TX`), sandbox off, hardened runtime on. Because the signing identity is stable, the Screen Recording permission survives rebuilds. If the certificate is missing, add `-allowProvisioningUpdates` to the build.
- Swift language mode 5 (`SWIFT_VERSION: "5.0"`), minimum macOS 13.

## Tests

```bash
scripts/test.sh                                   # everything, with a summary
scripts/test.sh ClipAppTests/TrimTests            # one class
scripts/test.sh ClipAppTests/TrimTests/testFurtherCutsGetNumberedNames
```

It runs `xcodegen generate` and `xcodebuild test -scheme ClipApp`, prints each test class with passed/failed, the failing assertions if there are any, and the totals; the exit code is non-zero if anything failed. The whole suite (135 tests) takes about half a minute after the build.

- `ClipAppTests` is an unhosted XCTest bundle: it is not loaded into ClipApp, because launching the app would start screen capture. It compiles the app sources it exercises itself (listed under `ClipAppTests` in `project.yml`): `Buffer/`, `Capture/CapturePrivacy.swift`, `Clip/`, `Encoding/`, `Library/ClipCatalog.swift`, `ClipEditing.swift`, `ClipInfo.swift`, `ClipTrimmer.swift`, `Settings/AppLanguage.swift`, `App/GameContext.swift`, `App/CaptureActivity.swift`. A file added to that list must not depend on SwiftUI views, `SettingsStore` or capture. A plain `xcodebuild build` does not build the tests.
- Nothing in the tests uses the screen, a permission or a device, and nothing but Swift and AVFoundation is used to check results. Every test writes into a temporary folder of its own that is removed afterwards.
- Logic tests: `RingBufferTests` (fake encoded samples from `Support/FakeSamples.swift`: GOP trimming, snapshots, byte limit, format change, audio), `NamingTests`, `GameMemoryTests`, `CapturePrivacyTests` (the setting's default and the filter decision), `CaptureActivityTests` (the start-at-launch setting's default, every clipping × recording combination and every transition between them), `CatalogTests` (real files in a temporary folder), `ClipInfoTests`, `TrimSelectionTests`, `AudioLevelsTests`, `UpdateSettingsTests` (the Sparkle keys in `ClipApp/Info.plist`, read from the source tree: an https feed, a 32 byte Ed25519 public key, daily checks, no automatic install, no system profile).
- Media tests: `Support/Synthetic.swift` produces a white bar moving over frames of noise, a 440 Hz tone as system audio and an 880 Hz tone as microphone, and runs them through the real `EncoderPipeline` (hardware H.264), `RingBuffer` and `ClipWriter`; `RecordingTests` feeds `RecordingWriter` the same way. `Support/MediaInspection.swift` reads the results back with `AVAsset`/`AVAssetReader` and measures the two tones with a Goertzel filter (`GoertzelTests` checks the meter itself). `ClipFileTests`, `TrimTests` and `RecordingTests` build on these.
- The background is noise on purpose: on a flat synthetic picture the encoder spends a fraction of its bitrate, and a precise cut of such a clip came out at about half the source's bitrate, which says nothing about real footage. With the noise the source reaches its 4 Mbps target and the precise cut measured 99 % of it.
- AVAssetWriter leaves its working copy (`<name>.mp4.sb-…`) next to a finished file for a fraction of a second after reporting completion. The tests that check a folder's contents wait for it to go; the library never lists it (it is not an `.mp4`).
- When a test fails, find out whether the app is wrong before touching the test.

## Architecture

Intended data flow:

```
SCStream -> CaptureManager -> EncoderPipeline (VideoToolbox H.264) -> RingBuffer
                           -> system audio -> AudioPipeline (16 bit PCM) -> RingBuffer
AVCaptureSession -> MicrophoneCapture -> AudioPipeline (16 bit PCM) ---> RingBuffer
shortcut -> HotkeyManager -> ClipWriter (RingBuffer snapshot -> mp4: video passthrough, audio AAC)
recording: EncoderPipeline + AudioPipelines -> RecordingWriter (fragmented mp4 on disk, alongside the RingBuffer)
```

Current code:

- `ClipApp/App/ClipAppApp.swift` — `Main` (the entry point: pins the language, then starts the SwiftUI app), the `MenuBarExtra` scene and `AppDelegate`; the shared objects (`PermissionManager`, `WindowManager`, `ClipController`) are owned by `AppDelegate`. At launch, without the Screen Recording permission the main window always opens on Settings, whose top is the Permissions section. Otherwise it opens on the clips unless `SettingsStore.openWindowAtLaunch` is off or the system started the app as a login item (read from the launch Apple event); a Dock click or a second launch reopens it (`applicationShouldHandleReopen`). Closing the last window never quits. Capture does not start at launch, except that clipping is started when `SettingsStore.startClippingAtLaunch` is on and the permission is granted, a launch as a login item included.
- `ClipApp/App/CaptureActivity.swift` — the clipping state machine as plain values (see "Clipping and recording" below): `isClipping` × `isRecording` → whether the stream runs, whether the buffer fills, what the window and menu offer, the menu bar icon, and the effects (`clearBuffer`, `fillBuffer`, `startStream`, `stopStream`) a change takes. Also the start-at-launch setting's key and default.
- `ClipApp/App/ClipController.swift` — builds the pipeline (`CaptureManager` -> `EncoderPipeline` -> `RingBuffer`, system audio and `MicrophoneCapture` -> `AudioPipeline` -> `RingBuffer`) and turns a request from the shortcut or the menu into a clip, filed under `Clips/<game>/`. The game comes from `GameTracker`, which follows `NSWorkspace.didActivateApplicationNotification` and feeds each activation to `GameMemory`, the rules as plain state (`App/GameContext.swift`): it is the frontmost app, or, when that is ClipApp itself or part of the system UI (Finder, Dock, Control Center, …), the last other app that was in front, as long as it left the front no longer ago than the buffer length; otherwise `Desktop`. So a clip saved with the button in ClipApp's window still goes to the game that was just played. The name is cleaned for use as a folder (`GameContext.folderName`). It holds the `CaptureActivity` and is the only place that changes it (`startClipping()`, `stopClipping()`, and the recording calls, through `setActivity`, which carries out the effects). The pipeline's output goes through `PipelineTap`: into the ring buffer only while clipping is on (switching it off resets the buffer under the same lock, so no sample slips in afterwards), into the running recording, and it remembers the newest video and audio formats. `startClipping()` without the Screen Recording permission asks for it the first time and opens Settings. A clip request while clipping is off (the shortcut) saves nothing and shows "Clipping is off" in the HUD, or as a notification if the HUD is off. It also owns recording: `startRecording()` marks the recording in the activity (which starts the stream if clipping is off), waits for the pipeline's video format and up to a second more for the audio sources that are on (5 s at most for video), builds a `RecordingWriter` from those formats, hands it to the tap and asks the encoder for a keyframe; `stopRecording()` closes the file and clears the recording from the activity, which stops the stream if clipping is off. With clipping on the replay buffer keeps filling meanwhile, and `AppDelegate.applicationShouldTerminate` waits for a running recording to be closed. Whenever `SettingsStore` changes, `applySettings()` pushes every setting down; each component ignores a value it already has. A changed capture source also empties the ring buffer, so a clip never mixes two sources, and switching the microphone on before its permission was ever asked for triggers the request (the one place for it, whether the switch was flipped in Settings or in the menu). The microphone only runs while the setting is on, the permission is granted and the stream runs; a permission change triggers `applySettings()` too. It watches `CaptureManager.state` and tells the user: immediately when the permission is missing, when capture fails to recover for more than 5 seconds, and when the selected source disappears and capture falls back to the main display. Every message goes out two ways (`report`): a system notification and, if `SettingsStore.showHUD` is on, the `HUD`. A notification about the missing permission opens Settings when clicked (`onOpenSettings`).
- `ClipApp/App/UpdateController.swift` — Sparkle 2 (Swift package, `from: 2.10.0`). One `SPUStandardUpdaterController`, created and started in `AppDelegate.init` and handed to the menu bar menu and Settings; it publishes `canCheckForUpdates` and wraps `automaticallyChecksForUpdates` (stored by Sparkle in the app's defaults). The configuration is in Info.plist through `project.yml`: `SUFeedURL` (https://ozturkmert1212.github.io/clip-app/appcast.xml, GitHub Pages from `docs/`), `SUPublicEDKey`, `SUEnableAutomaticChecks`, `SUScheduledCheckInterval` 86400, `SUAutomaticallyUpdate` and `SUAllowsAutomaticUpdates` off (an update is offered, never installed without asking, and the alert has no option to change that), `SUEnableSystemProfiling` off. Debug builds only: an `SPUUpdaterDelegate` returns `ClipAppFeedURLOverride` from the defaults (`-ClipAppFeedURLOverride <url>` on the command line) as the feed; Release does not compile it. Sparkle itself also takes a feed from an `SUFeedURL` user default ahead of Info.plist, in Release too; harmless, because an update must carry an EdDSA signature from the key in the running app or be code signed by the same team. Sparkle accepts an update when the EdDSA signature matches the running app's key or the code signature matches; either may change on its own, never both. Sparkle's windows (update alert, progress) are localized by Sparkle and follow the launch language, like other text supplied by macOS.
- `ClipApp/Capture/CaptureManager.swift` — the `SCStream` lifecycle. The source (`CaptureSource`: display / window / application) is resolved again on every start; if it is gone, capture falls back to the main display. All (re)starts go through a single `restart()`: stream errors (with growing delay), display parameter changes, wake from sleep, the target application launching or quitting. Frames arrive in `StreamOutput` on the capture queue and are handed out through `onVideoFrame`. System audio comes from the same stream (`capturesAudio`, 48 kHz stereo, our own audio excluded) on a separate queue; turning it on or off rebuilds the stream. With a window or application source only that application's audio arrives. With a display source the filter is `SCContentFilter(display:excludingApplications:exceptingWindows:)`, built from `CapturePrivacy` (`Capture/CapturePrivacy.swift`, plain values, tested): Notification Center (`com.apple.notificationcenterui`) is always excluded as an application; ClipApp itself too while `showsClipApp` is off (the default), which keeps the main window, its sheets and menus and the HUD out of clips. `excludedWindowIDs` (the HUD) is passed through `exceptingWindows` when ClipApp is shown (`SettingsStore.showClipAppInCaptures`) and as a fallback when ClipApp is not found in the shareable content, so the HUD never ends up in a clip. A change of `showsClipApp` does not restart capture: `updateFilter()` hands the running stream a new filter for the same display with `updateContentFilter`, so the encoder session, the ring buffer and a running recording carry on (a window or application source has nothing to change; a filter built while the value changed is corrected right after the start). ClipApp is never offered as a source, and a stored window or application source owned by ClipApp is treated as gone (main display fallback). While applications are excluded, another application's window passed as an exception is not captured either (measured). The applications are looked up separately with `onScreenWindowsOnly: false` (`exclusions()`) and the log says "N own window(s) and M app(s) excluded" (normally 0 and 2). If Notification Center restarts, the stream is rebuilt.
- `ClipApp/Capture/MicrophoneCapture.swift` — captures the default input device with `AVCaptureSession` (SCStream's microphone is macOS 15+ only). It asks for 48 kHz output so it can be mixed with system audio. Timestamps are converted from the session clock to the host clock. Rebuilt when the default device changes and on a session error.
- `ClipApp/Encoding/EncoderPipeline.swift` — `VTCompressionSession` (hardware H.264, real time, no B-frames, 2 s keyframe interval). The session is rebuilt on the first frame, when the frame size changes and after `configure(fps:bitrate:)`. `requestKeyframe()` forces the next frame to be one, which is where a recording starts.
- `ClipApp/Encoding/AudioPipeline.swift` — converts incoming LPCM (Float32 or Int16, planar or interleaved) to 16 bit interleaved stereo PCM while applying the level (mono is copied to both channels). One per audio source.
- `ClipApp/Buffer/RingBuffer.swift` — encoded video samples and PCM audio per track (`AudioTrack`: system, microphone), guarded by a lock. It only trims when a keyframe arrives, and by whole GOPs. When the format (resolution) changes the old content is dropped, because a single mp4 track cannot change parameter sets. There is also a byte cap (`SettingsStore.bufferByteLimit` = buffer length × target bitrate × 3): beyond it the oldest GOPs are dropped regardless of age, the GOP being filled always stays. While the cap is active the buffer is shorter than configured and the menu shows an info line (`ClipController.byteLimitedSeconds`). Audio is trimmed by duration; when an audio format changes, that track's old content is dropped.
- `ClipApp/Clip/ClipWriter.swift` — mp4 through `AVAssetWriter`: video passthrough, audio AAC. With two audio sources of the same format the first audio track is their sum (`mix`, enabled, what every player picks); with `keepStems` each source follows as a track of its own with `marksOutputTrackAsEnabled = false` (order: mix, system, microphone). One source gives one ordinary track; sources at different sample rates cannot be summed and stay two ordinary tracks. The layout is recorded in the file's `ClipInfo`. An unwritable folder and a full disk come back as distinct errors and the partial file is deleted. The caller supplies the file name (`ClipNaming`); if it exists, `_2`, `_3` are appended (`ClipNaming.uniqueURL`, also used for recordings and moves).
- `ClipApp/Clip/ClipNaming.swift` — file names, with nothing to configure: a clip is `<game>_<yyyy-MM-dd>_<HH-mm-ss>` (the game as cleaned by `GameContext.folderName`, cut to 60 characters in the file name only), a recording `Recording_<date>_<time>`. `renamed(_:from:to:)` decides what a move to another game does to the name: a clip whose name is still the automatic one for the game it is in (optionally with a `_2` clash suffix or the editor's "(trimmed)"/"(edited)" ending) gets the new game's name with the same date and time; any other name was given by the user, or predates this scheme, and is left alone. A `fileNameFormat` left in `UserDefaults` by older versions is simply never read.
- `ClipApp/Clip/RecordingWriter.swift` — a recording, written while it runs: the encoder's samples as they are (starting at the first keyframe, the newest frame held back so the last one can be stretched to the end), audio in the same track layout as a clip. `AudioGroup` does for a live stream what `ClipWriter.audioTimeline` does for a snapshot: buffers back to back, holes over 20 ms filled with silence, a source more than 0.5 s behind padded so it cannot stall the others, and whatever all sources have reached written per source and as their sum. `movieFragmentInterval` is 5 s, so a recording cut off by a crash stays playable up to the last fragment. A change of the capture size ends the recording (one track cannot change parameter sets).
- `ClipApp/Hotkey/HotkeyManager.swift` — global shortcut through KeyboardShortcuts (default ⌃⌥⌘R, changeable in Settings) for saving a clip, and a second one for starting and stopping a recording that has no default. When triggered it logs at notice level in the `hotkey` category.
- `ClipApp/Permissions/PermissionManager.swift` — Screen Recording, microphone and notification permission state, refreshed every 5 seconds and whenever the app becomes active, plus requests, System Settings deep links and relaunch. Screen Recording has no "not asked yet" in the system, so the app remembers whether it asked (`screenRecordingStatus`); once asked and still not granted, the row says that a running process keeps seeing the old answer and offers Restart ClipApp. Input Monitoring is not needed: the global shortcuts are Carbon hot keys.
- `ClipApp/Notifications/Notifier.swift` — system notifications: "Clip saved" and "Recording saved" (with a Show in Finder action) and error messages. Without the permission it silently does nothing.
- `ClipApp/Settings/SettingsStore.swift` — `UserDefaults` backed settings: buffer length, resolution, FPS, bitrate, capture source, save folder (`saveDirectory`, with `clipsDirectory` = `Clips/` and `videosDirectory` = `Videos/` under it), on/off and level (0–2, 1 = unchanged) for system audio and microphone, keeping each audio source as a separate track for the editor (`keepAudioStems`, default on), what saving an edited clip does (`editSaveMode`: ask, new clip, replace), the on-screen message (`showHUD`, default on) and its corner (`hudCorner`), showing ClipApp's own windows and menus in clips and recordings (`showClipAppInCaptures`, key `showClipAppInCaptures`, default off, also when nothing is stored; the HUD is never shown), starting clipping at launch (`startClippingAtLaunch`, key `startClippingAtLaunch`, default off), opening the main window at launch (`openWindowAtLaunch`, default on), interface language (`language`). Stored values are validated against the offered options. Launch at login goes through `SMAppService`; the system owns that state, it is not written to `UserDefaults`. Because the login item is registered for the app's current path, the option can only be turned on when running from `/Applications` (or `~/Applications`).
- `ClipApp/Settings/AppLanguage.swift` — the interface language (English, Turkish), see "Localization".
- `ClipApp/Library/` — `ClipCatalog` (plain file system work: where clips and recordings go, `list(_:)` and `move(_:toGame:root:)`), `ClipLibrary` (the observable wrapper around it for the window: the mp4 files under the save folder, newest first: `Clips/<game>/` as that game's clips, files lying directly in the save folder or in `Clips/` as "Other" (the layout before games; never moved automatically), `Videos/` as recordings. One FSEvents stream on the save folder triggers reloads, which also catches a file that is still growing. A clip's game is the folder it sits in; `move(_:toGame:)` moves files between folders and renames those that still carry their automatic name, see `ClipNaming`), `ClipInfo` (game, bundle ID, time, audio track roles and the editor's levels, stored in the mp4 itself as a JSON string in the iTunes comment field, so it survives renaming and moving and shows up as `comment` in ffprobe; the game in it is the one the clip was recorded in and does not follow a move), `ThumbnailCache` (`AVAssetImageGenerator` off the main thread, JPEG files under `~/Library/Caches/<bundle id>/Thumbnails`, keyed by path, size and modification date), `ClipEditing.swift` (`TrimSelection`, the range between the editor's two handles with its clamping, and `AudioLevels`, the two sliders and mute switches and how they become gains and stored levels; `ClipPlayerModel` holds its state in these), `ClipTrimmer` (writes `<name> (trimmed).mp4` or `(edited).mp4` next to the original, or over the original through a hidden temporary file that is swapped in with `replaceItemAt` only when complete. A plain cut is an `AVAssetExportSession` passthrough. Everything else goes through `AVAssetReader`/`AVAssetWriter` (`rewrite`): the video copied or, for the precise option, encoded as H.264 at the source track's `estimatedDataRate`, size, frame timestamps and color tags; audio tracks copied with their enabled state, or, with an `AudioEdit`, a new mix rendered by `AVAssetReaderAudioMixOutput` at the chosen levels in front of the two untouched source tracks).
- `ClipApp/UI/` — `MainWindowView` (sidebar: a Clips section with All Clips, one row per game with the app's icon and clip count, and Other; a Videos section; pinned to the bottom, Settings and below it the status strip: "Clipping off" and an indigo Start Clipping button while clipping is off; "Clipping · <source> · N s buffered", the save button and below it a neutral Stop Clipping button, both full width, while on (a title that does not fit wraps to a second line); recording time; the recording button), `ClipsView` (thumbnail grid for the selected sidebar row, multi-selection with Command and Shift clicks and Command-A, a selection bar with the batch actions, context menu, empty state), `ClipPlayerView` (AVKit player with the trim timeline, and for clips with separate source tracks a row per source with waveform, level 0–150 % and mute; the preview then plays an `AVMutableComposition` of the video and the two source tracks with an `AVAudioMix`, because the file marks them disabled), `LanguageRoot`, `MenuBarView` (the menu bar menu as a quick control panel: status ("Clipping off", "Clipping · source · N s buffered", "Recording · source" when only a recording runs), or the missing permission as an item that opens Settings; Start Clipping while clipping is off, Save and Stop Clipping while it is on; start/stop recording; a Source submenu fed by `CaptureManager.sources`, with a note that changing it clears the buffer and its rows disabled during a recording; switches for microphone and system audio bound to the same `SettingsStore` values as Settings; Open ClipApp, Check for Updates… (disabled while a check runs), Settings…, Quit. Nothing that is a preference lives here), `SettingsView` (the Settings tab; its first section is Permissions: one row each for Screen Recording, Microphone and Notifications with the live status and one action, Request before the system has asked and Open System Settings after. There is no separate permission window. Above About, an Updates section: the daily check switch, the current version and build, and Check for Updates…), `WindowManager` (hosts the main window's SwiftUI view in an AppKit window; with `LSUIElement` this is the reliable way to open a window conditionally at launch. `LSUIElement` stays in Info.plist: showing the main window switches the activation policy to `.regular`, closing it back to `.accessory`, so the Dock icon exists exactly while the window is open. The main window is 960×640 by default, 760×480 minimum, and remembers its frame), `WindowSharing` (sets `sharingType` of every ClipApp window to `.readOnly` while `showClipAppInCaptures` is on and `.none` while it is off, windows opened later as they come on screen; the HUD is left at `.none`), `HUD` (a borderless `NSPanel` shown for 2.5 seconds in the chosen corner: ignores mouse events, at `.screenSaver` level, on all Spaces and above full screen apps. The corner is `SettingsStore.hudCorner`, default top left; top right is where notification banners appear, so the HUD would sit on top of the banner there).
- `ClipApp/Resources/` — `Localizable.xcstrings` and the per-language `InfoPlist.strings`.

## Look

The interface stays standard macOS (system font, system materials, native menu and window chrome) and takes its colors from the app icon. All of it is defined in `ClipApp/UI/Brand.swift`; a view never spells out a color, a radius or a spacing itself.

- Palette: indigo #4B3FD1 / #2A2392 / #150F4F, lavender #E4E0FF / #C9C4FF, record red #FF3B4E to #D3112B. Red only ever means recording.
- `Brand.accent` is the tint of the SwiftUI controls: #4B3FD1 in light mode, #8F87FF in dark mode. `LanguageRoot` applies it with `.tint`, so toggles, sliders, pickers and button titles are indigo whatever accent color the system is set to. macOS writes picker values and bordered button titles in the tint, so in dark mode it has to be light enough to read as text (4.7:1 on the grouped background; #6A5FF0 was tried first and gave 3.6:1).
- Because that dark tint is too light under white text (3:1), fills that carry white text use `Brand.fill`: #4B3FD1 in light mode, #574BDB in dark mode (7.2:1 and 6.1:1). The same pair is the asset catalog's `AccentColor` (`ASSETCATALOG_COMPILER_GLOBAL_ACCENT_COLOR_NAME`), which is what AppKit draws with while the system accent color is Multicolor: the sidebar's selection, focus rings, an alert's default button, a menu's highlighted item. So the SwiftUI tint and the AppKit accent differ in dark mode on purpose: one is read as text, the other sits under white text. Our own filled buttons use `Brand.primaryGradient` (`PrimaryButtonStyle`: Save Last N Seconds, Save Edited Clip, the sheet's Save). A system prominent button would put white on the tint; do not use `.borderedProminent`.
- `Brand.accentText` is for our own indigo marks on the window background (sidebar icons, the status dot, card frames): indigo in light mode, lavender in dark mode.
- The recording button fill starts at #E0203A rather than the icon's #FF3B4E, on which white text would be 3.5:1; the bright red is used for the dot.
- The sidebar is an ordinary `List(selection:)`: arrow keys move the selection (which is applied as it moves, so Return has nothing left to confirm) and VoiceOver announces the selected row. Its highlight is AppKit's and takes the asset `AccentColor`; `.tint` and `listRowBackground` have no effect on it (both tried). If the user picks a specific accent color in System Settings, the highlight follows that instead, as in every Mac app. Row icons turn white on the highlight through `backgroundProminence` (macOS 14+; on 13 simply when selected). Settings is pinned below the list and is a button drawn to match; a local key monitor, active only while the list has keyboard focus, carries Down from the list's last row to Settings and Up back, so the sidebar is one run for the keyboard.
- Status is never color alone: the dot sits next to its text, problems show a warning sign instead of a dot, permission rows have a symbol and a word. `RecordDot` pulses only when Reduce Motion is off, and so does the card's lift under the pointer.
- The menu bar shows the icon and nothing else, no text and no counter (`MenuBarIcon`, from the `MenuBarIcon` image set, 18×18 pt with 1x and 2x artwork). While clipping it is the template image, which the menu bar colors itself; while clipping is off (and nothing is recorded), or capture is failing or not permitted, it is the same template at half opacity (`CaptureActivity.icon`); during a recording it is a non-template image drawn on demand: the artwork without its dot in `NSColor.labelColor`, and the dot in #FF3B4E. SwiftUI hands these very `NSImage` objects to the status item's button (checked), so the drawing handler runs under the button's own appearance and at its scale: the ring is light on a dark menu bar and dark on a light one without any observing, and it is redrawn when the appearance changes.
- `BrandGlyph` draws the icon's mark (an arrow circling a dot) for empty lists; `BrandBadge` is the small logo in Settings > About. It is drawn in code because `NSApp.applicationIconImage` comes back tinted or clear when the user has chosen that icon style in macOS.
- Checked by rendering the main window of a second instance on a library of synthetic clips, in light and dark and in English and Turkish: clip grid with a selection, Settings, the editor, both empty states, a running recording and the About section. Not checkable that way: hover states, focus rings (they follow the system accent, not the tint), the menu bar menu's dot, alerts, and anything under Increase Contrast or Reduce Motion.

## Localization

- The source language is English (`developmentLanguage: en`), Turkish is the second language. Every user-visible string lives in `ClipApp/Resources/Localizable.xcstrings`; the key is the English text. SwiftUI literals are looked up as `LocalizedStringKey`; everything outside a view (notifications, HUD, errors, window titles) and every menu bar menu item uses `AppLanguage.string(_:)`, never `String(localized:)` directly (that one follows the launch language). Log messages and code comments stay in English and are never localized.
- The catalog is maintained by hand (Xcode also syncs it when the project is built in the IDE). `SWIFT_EMIT_LOC_STRINGS` is on, so after a build the keys the compiler found are in `build/Build/Intermediates.noindex/ClipApp.build/<config>/ClipApp.build/Objects-normal/arm64/*.stringsdata`; comparing those with the catalog's keys shows a missing or stale entry. A key missing from the catalog shows up in English in the Turkish interface.
- Usage descriptions (currently only `NSMicrophoneUsageDescription`) are localized in `ClipApp/Resources/{en,tr}.lproj/InfoPlist.strings`; the value in `project.yml` is the English fallback.
- The language does not follow the system and changes without a restart. `AppLanguage.string(_:)` looks a string up in the chosen language's own `.lproj` bundle on every call (English has no table there, its keys are the text); `LanguageRoot` wraps every hosted SwiftUI tree (main window, menu and puts `SettingsStore.language.locale` into the environment, which is what the literals resolve against. Things that hold a finished string have to be refreshed by hand: the notification action title (`Notifier.registerActions()`, run before each clip notification), the source list in Settings (reloaded on change), and pickers whose rows are plain strings (`.id(settings.language)`).
- Text supplied by macOS stays in the launch language until a restart: the app menu, the shortcut recorder, the player controls, open panels, display names (`NSScreen.localizedName`, visible in the status strip and the menu). For that part `AppLanguage` still writes the app's own `AppleLanguages`, and `Main.main()` calls `AppLanguage.applyAtLaunch()` before SwiftUI starts, so without a stored choice the app comes up in English even on a Turkish system. ## Notes

Notification banners: macOS hides notifications by default while the screen is shared or recorded ("display shared"). The notification lands in Notification Center but no banner appears; the user has to allow notifications during sharing under System Settings > Notifications. That switch cannot be flipped from code; the Notifications row in Settings > Permissions offers a button that opens the page, and the real feedback is the HUD. Even with that switch on, banners stay out of clips, because Notification Center is excluded from the display filter. Side effect: desktop widgets are Notification Center windows too, so they do not appear in display clips.

Keeping our own interface out of clips: by default ClipApp is excluded from display capture as an application, and its windows have `sharingType = .none`. With Settings > General > Show ClipApp in recordings on, ClipApp stays in the filter, its windows are `.readOnly`, and only the HUD (`sharingType = .none` always) is excluded, by window ID. On recent macOS versions ScreenCaptureKit is known to ignore `sharingType`, so the filter is the path to rely on; if one of the two is ever removed, the filter has to stay. Measured on macOS 27.2 at filter level, not from a saved clip: a still taken through a display filter that excludes ClipApp and Notification Center did not contain the main window, the same still without exclusions did (mean difference to the window's own image 15.8 against 0.4 on a 0–255 scale). The HUD under the application exclusion was not measured again; the earlier measurement (HUD and banner rectangles over a magenta background never changed in the clip) was taken with the HUD excluded by window ID.

Show ClipApp in recordings, measured on macOS 27.2 in the running Debug app through a temporary hook (not committed), on a 1920×1080 main display: the main window open, a recording running, the setting switched off → on → off with 3.5 s per phase, the HUD shown in the top left corner 1.2 s before the end of each phase and a clip written from the ring buffer at the end of each. The window's area in the frame without the HUD differed by 37.1 and 37.3 (mean, 0–255) between the off and on phases and by 1.8 between the two off phases; looking at the frames, the window was there only in the on phase. The HUD's area differed by 0.00, 0.25 and 0.00 between the frames without and with the HUD, i.e. it was in none of them. The log showed one "Capture started" and two "Capture filter updated" lines, the ring buffer's oldest sample was the same before and after each switch, and the recording was a single 15.7 s 1920×1080 file across both switches with no gap between frames over 33 ms. Not covered: the menu bar menu and sheets in a clip (they belong to the same application, which is what the filter includes or excludes), and whether the HUD was actually drawn on screen during the test (it cannot be screenshotted).

Trimming (measured on a 1080p60 clip, range 5.3–12.7 s): passthrough export does not cut on a keyframe. It keeps the frames back to the previous keyframe (0.6 s here, at most one 2 s GOP) and hides them with an edit list, like `ClipWriter` does, so the result plays as exactly 7.400 s and its first visible frame is the source frame at 5.3 s; a player that ignores edit lists shows the extra frames. The precise option on the same range: 40.01 Mbps against 40.27 Mbps for the source track (99 %), 1920×1080, the same 425 frames, no hidden frames, PSNR 41.7 dB / SSIM 0.984 against the source, audio identical to the passthrough result. An export preset is not used for it because `AVAssetExportPresetHighestQuality` picked 15.5 Mbps for this clip. Cancelling mid-way throws `CancellationError` and removes the partial file (tested from the command line, not through the Cancel button).

The encoder only aims at the average bitrate: on content that does not compress, such as pure noise, it goes far above the target (~150 Mbps measured at 1080p60), which is why RingBuffer has a byte cap: on such content the clip comes out shorter than configured but memory stays bounded. On compressible synthetic moving content it stayed below the target.

To read logs use `/usr/bin/log` (zsh has its own `log` builtin): `/usr/bin/log show --predicate 'subsystem == "com.mertozturk.ClipApp"' --last 1m --info`.

Known limit: the global shortcut does not fire in full screen (exclusive) games, the game grabs the keyboard; it works in borderless/windowed mode.

Clip timing (read before changing):

- ScreenCaptureKit only delivers a frame when the screen changes. So the end of a clip is not the newest sample but the host clock at the moment of the request; `endSession` holds the last frame until then.
- A clip is written from the last keyframe before the requested start. The frames before the start (lead-in) only exist so the first visible frame can be decoded; the writer trims them from playback with an edit list.
- Lead-in frames are shifted forward so the last one lands exactly on the clip start. That way the lead-in is at most one GOP long even if the screen was static for a long time, and the clip is exactly N seconds.
- The duration of the last video frame is extended to the end of the clip. `endSession` alone is not enough: with an audio track present the video track ends at the last frame, and ffmpeg based players do not see the extension.
- Audio is laid out gaplessly on the clip timeline (`audioTimeline`): buffers are placed end to end, holes larger than 20 ms and the start and end of the clip are filled with silence. Every audio track is therefore exactly as long as the clip and the AAC encoder is unaffected by timestamp jitter.

Audio tracks and the editor (measured with synthetic input: moving bars as video, a 440 Hz tone as system audio, an 880 Hz tone as microphone):

- A clip and a recording with both sources: track 1 holds both tones and is enabled, track 2 only 440 Hz, track 3 only 880 Hz, both disabled (`AVAssetTrack.isEnabled` false, ffprobe `disposition:default=0`). Without the microphone there is a single track.
- Recording: a microphone that started 1 s late and paused from 4 s to 5 s came out with silence in exactly those places; killing the process at 12.5 s left a file that AVFoundation and ffmpeg read as 10.0 s without errors.
- `AVMutableAudioMixInputParameters` volumes above 1 do amplify (1.5 gave 1.5 times the RMS), which is what the 150 % of the level sliders relies on. `AVAssetExportSession` with the passthrough preset completes but ignores an `audioMix`, so an audio edit never goes through it.
- An `AVAssetReaderTrackOutput` without output settings and with a `timeRange` that starts inside a GOP delivers the frames from the previous keyframe on, marked do-not-display, plus marker buffers without samples; all of them are passed to the writer, which turns them into the edit list. The first visible frame of such a cut was identical to the source frame at that time.
- Editor save at system 50 %, microphone muted: the new mix had the 440 Hz tone 6 dB lower and no 880 Hz tone, the two source tracks were unchanged, the levels were in the file's `ClipInfo` and came back as the sliders' positions.
- Replacing the original: a save cancelled mid-way left the original byte-identical with no temporary file behind; a completed one kept the creation date.
- Size: the two extra AAC tracks cost about 48 KB per second at the 192 kbps target, i.e. about 1.4 MB per 30 s clip, under 1 % of a 40 Mbps clip and about 10 % of a 4 Mbps one.

Menu and permissions, checked in the running app: the real `NSMenu` items were read back in the order above; flipping the microphone setting changed the menu item's check mark; choosing another display restarted capture and the buffered time dropped from 7 s to 1 s; during a recording the item read "Stop Recording (0:01)", the note changed and the source rows were disabled. With the Screen Recording check forced to fail, a launch with "open window at launch" off still opened the window on Settings with the row showing Not granted, Open System Settings and Restart ClipApp, and capture did not start. Not exercised: clicking any of it, and the real system prompts (the permissions are granted on this Mac).

Naming, checked in the running app with Chess as the game: the real shortcut with Chess in front and a save with ClipApp in front both gave `Clips/Chess/Chess_<date>_<time>.mp4`, a recording `Videos/Recording_<date>_<time>.mp4`. Moving everything to "Rocket League: 2026/Edition" renamed the automatically named clip to `Rocket League 2026 Edition_<same date and time>.mp4` and left a clip renamed by hand ("my best goal") and an old-style `Clip_…` file with their names. A template stored by an older version was present during the test and had no effect.

Game detection, tested in the running app with Chess as the game and a 15 s buffer: the real shortcut pressed with Chess in front gave `Clips/Chess`; saving with ClipApp in front 3 s after leaving Chess gave Chess, as did Chess, then Finder, then ClipApp 11 s later; 24 s after leaving Chess it gave `Desktop`. The saves from ClipApp were triggered by calling `saveClip()` while its window was frontmost, not by clicking the button.

Clipping and recording (`CaptureActivity`, read before changing):

| clipping | recording | stream | buffer fills | window / menu offer |
|---|---|---|---|---|
| off | off | stopped | no | Start Clipping |
| on | off | runs | yes | Save Last N Seconds, Stop Clipping |
| off | on | runs | no | Start Clipping |
| on | on | runs | yes | Save Last N Seconds, Stop Clipping |

Start/Stop Recording is always offered. Leaving clipping empties the buffer; the stream stops when neither is on, which also takes away the system's screen recording indicator and the microphone. Settings (source, resolution, …) are stored and pushed to `CaptureManager` while it is stopped and only take effect at the next start (`configuration` restarts only a wanted stream; the filter update needs a running one). A stream that is started again begins with fresh formats (`PipelineTap.forgetFormats`).

Checked in the running Debug app through a temporary hook (not committed), with a temporary save folder passed as `-saveDirectory`: at launch the state was idle with no frames; a clip request then logged "clipping is off" and wrote nothing; Start Clipping started capture and 6 s later a clip came out at 6.0 s (all the buffer held); Stop Clipping left the state idle, 0 frames and no snapshot in the buffer; a recording with clipping off started capture by itself, the buffer stayed empty, the file was 4.8 s for a 5 s request (time to the first frame) and capture was idle again after it; Stop Clipping during a recording emptied the buffer while capture and the recording ran on, and the recording was one 5.0 s file. Launching with `-startClippingAtLaunch '<true/>'` started capture, without it nothing started. Not checked: clicking the buttons and menu items, the shortcut itself (a keystroke synthesized with System Events did not reach it), the permission path of Start Clipping, how the dimmed and normal icons look.

Design rules:

- Raw frames are never kept in memory; RingBuffer stores video only as encoded `CMSampleBuffer`s and trims by GOP, a clip always starts with a keyframe.
- Audio is deliberately kept as PCM and encoded to AAC when the clip is written: it can be cut and padded with sample accuracy, and the writer takes care of encoder delay (priming). 16 bit stereo 48 kHz is 192 KB per second, small next to the video.
- All tracks are kept on the same host clock and rebased from one common start time when the clip is written.
- Writing a clip does not stop capture.

## Releasing

Order, do not change it: the appcast must never point at a file that is not uploaded yet.

1. Bump `MARKETING_VERSION` and `CURRENT_PROJECT_VERSION` in `project.yml`, run `scripts/test.sh`.
2. `IDENTITY="F530879D8F391FDD191902415739BEF130C263D4" scripts/release.sh`: build, sign Sparkle's nested code inside out (`XPCServices/*.xpc`, `Autoupdate`, `Updater.app`, the framework) and then the app, each with the same identity, `--options runtime` and `--timestamp` and without `--deep`; notarize and staple the app (as a zip), build the dmg around it, sign, notarize and staple the dmg; print the SHA-256. `--no-notarize` builds, signs and packages only.
   The dmg is built by [dmgbuild](https://github.com/dmgbuild/dmgbuild) (`python3 -m pip install --user dmgbuild`; the script stops if it is missing), which writes the install window into the image's `.DS_Store` itself, without Finder or AppleScript. `scripts/dmg/settings.py` holds the layout: volume name ClipApp, HFS+, UDZO, a 660×400 icon view with status bar, sidebar, toolbar, path bar and tab bar hidden, 112 pt icons with 12 pt labels below them, ClipApp.app at (165, 200) and the Applications link at (495, 200), not rearranged. `scripts/dmg/background.png` (660×400) and `background@2x.png` (1320×800) are the source pictures; `background.tiff` is what is used, both in one file (`tiffutil -cathidpicheck background.png background@2x.png -out background.tiff`, rerun after changing a picture), so Retina screens get the 2x one. dmgbuild puts it at the root of the image as the hidden `.background.tiff`. Measured on macOS 27.2: the window frame and the content are both 660×400, the title bar is drawn over the top of the content, so the picture keeps its top part free.
3. Update `release-notes.md` (gitignored, it is the release body), commit, `git push`.
4. `git tag v<version>`, `git push origin v<version>`, `gh release create v<version> dist/ClipApp-<version>.dmg --title "ClipApp <version>" --notes-file release-notes.md`.
5. Only after the asset is uploaded: `scripts/appcast.sh dist/ClipApp-<version>.dmg <version> <build>`. It signs the dmg with `sign_update` (EdDSA, private key in the login keychain, default account) and adds an item at the top of `docs/appcast.xml` (created with its header and `docs/.nojekyll` the first time) pointing at `releases/download/v<version>/ClipApp-<version>.dmg`, with `sparkle:version` = build, the short version, `minimumSystemVersion` 13.0 and the release page as `fullReleaseNotesLink`. ## graphify notes

- `graphify-out/` is in `.gitignore`. Reason: the post-commit hook regenerates the graph after every commit; if the folder were in the repo, every commit would leave the working tree dirty again. The graph is produced deterministically from the code, so `graphify update .` always brings it back.
